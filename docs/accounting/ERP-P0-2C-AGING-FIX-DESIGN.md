## 1) الخلاصة التنفيذية

1. **العيب مؤكد ومرصود في موضعين على الأقل (لا موضع واحد):**
   - `AgingReportQueries.GetAgingAsync` (فرع العملاء) — السطر 34: `bal = s.TotalAmount - s.PaidAmount`.
   - `ReportServiceReportsB.cs` — السطور **11 و15**: نفس الصيغة `s.TotalAmount - s.PaidAmount` في تقريرين آخرين (أعمار/فواتير مفتوحة).
2. **جذر السبب البنيوي (دليل حاسم):** `SalesInvoice.PaidAmount` يُكتب في **موضع واحد فقط** — `SalesInvoiceService.Create.cs:170` عند **إنشاء** الفاتورة
   (`type == Cash || paymentMethod == Check ? TotalAmount : 0m`) — **ولا يوجد أي كود يُحدِّثه بعد ذلك**: لا سند قبض، ولا مردود، ولا شيك.
   ⇒ **الفاتورة الآجلة تبقى `PaidAmount = 0` دائمًا** ⇒ التقرير يعرض **إجمالي الفواتير الآجلة** لا **المتبقي**.
3. **لا يوجد كيان تخصيص للعملاء:** الكيان الوحيد هو `PaymentAllocation` (**جانب الموردين/سندات الصرف**). ⇒ سندات القبض **لا تُخصَّص** على الفواتير إطلاقًا (تحرّك الأستاذ ورصيد العميل فقط).
4. **النموذج المرجعي الصحيح موجود في المشروع:** `SupplierAllocationQueries.GetResidualAsync` — السطر 130:
   `residual = TotalAmount − PaidAmount − returns − netAllocations` ⇒ **يمكن قياسه للعملاء بعد اعتماد سياسة**.
5. **التوصية:** اعتماد **الخيار C** (تخصيص يدوي + FIFO + إبراز غير المخصص) كهدف نهائي، مع **مرحلة تمهيدية فورية**: (أ) إصلاح شروط الاستعلام (Posted + asOf) بلا تغيير سياسة، (ب) حساب المتبقي للعملاء بنفس نموذج الموردين **بعد** قرار التخصيص.

## 3) مقارنة السياسات (A/B/C)

| البُعد | **A: تخصيص يدوي** | **B: FIFO تلقائي** | **C: يدوي + FIFO + إبراز غير المخصص** |
|---|---|---|---|
| رصيد الفاتورة المتبقي | دقيق ومقصود | دقيق حسابيًا | دقيق + مدقَّق |
| أعمار الذمم حسب تاريخ القطع | ✅ دقيق | ✅ دقيق | ✅ دقيق (+ تقرير غير مخصص) |
| قبض جزئي/كامل | يتطلب إدخال تخصيص لكل قبض | يُوزّع تلقائيًا | يدوي أو تلقائي باختيار المستخدم |
| مردودات المبيعات | تُخصم يدويًا من الفاتورة الأصلية | تُخصم تلقائيًا من فاتورتها | تُخصم تلقائيًا (إلزاميًا) — الأصل واضح |
| شيكات تحت التحصيل | **لا تُخصم** حتى التحصيل (سياسة) | نفسها | نفسها + إظهار مبلغ «تحت التحصيل» منفصلًا |
| شيك محصَّل | يُخصَّص كتحصيل | يُوزّع FIFO | كـA/B |
| شيك مرتجع | يُلغى أثره ويعود المتبقي | يُعاد تلقائيًا | يُعاد تلقائيًا + سجل تدقيق |
| الإلغاء والعكس وإعادة الترحيل | يحتاج إلغاء التخصيص يدويًا (خطر نسيان) | يُعاد الحساب | يُدار بقيود صريحة + سجل |
| التقارير التاريخية والتدقيق | يعتمد على التخصيصات المخزَّنة (قابلة للتدقيق) | إعادة حساب ⇒ **قد تتغيّر نتائج تاريخية إن تغيّر ترتيب المستندات** | الأفضل للتدقيق (تخصيص مخزَّن + غير مخصص مرئي) |
| كمية العمل التشغيلي | عالية على المستخدم | منخفضة | متوسطة (تلقائي افتراضيًا + تعديل يدوي) |
| المخاطر | ترك قبض **بلا تخصيص** ⇒ ذمم مرتفعة (نفس العيب الحالي) | تخصيص خاطئ يفسّر مطالبات/فواتير خاطئة | مخاطر A+B مُدارة بالمراجعة |
| يحتاج تغيير مخطط؟ | **نعم** (كيان تخصيص للعملاء) | نعم | **نعم** (تخصيص + حالة غير مخصص) |

**تقييم مهني:** الخيار **C** هو الوحيد الذي يجعل **المجموع متسقًا دائمًا** (الذمم + غير المخصص + تحت التحصيل = رصيد الأستاذ)، وهو ما يمنع تكرار P0-2. لكنه **يتطلب Migration** ⇒ **ممنوع الآن**.

## 4) عيوب شروط الاستعلام — خطة اختبار محددة

| # | الفحص | كيف يُختبر | النتيجة المتوقعة |
|---|---|---|---|
| Q1 | **لا فواتير غير مرحَّلة في تقرير العملاء** | إنشاء فاتورة بحالة غير `Posted` (عبر مسار يسمح) + تشغيل الأعمار | يجب ألّا تظهر؛ حاليًا (`Status != Cancelled` فقط) **قد تظهر** ⇒ اختبار يجب أن يفشل قبل الإصلاح |
| Q2 | **احترام `InvoiceDate <= asOfDate`** | فاتورة بتاريخ +30 يومًا + تشغيل الأعمار بـ`asOf = اليوم` | يجب ألّا تظهر؛ حاليًا **تظهر** (لا فلتر) ⇒ اختبار يفشل قبل الإصلاح |
| Q3 | **اتساق قواعد العملاء/الموردين** | مقارنة الاستعلامين: `Posted` · `asOf` · مصدر المتبقي | العملاء: 0/2 مطابق ⇒ يجب توحيد القاعدتين حيث تتساوى القواعد المحاسبية |
| Q4 | **عدم احتساب المقبوض/المردود مرتين** | بعد التخصيص: قبض مخصَّص جزئيًا + مردود مرتبط ⇒ مجموع (ذمم + غير مخصص) = أستاذ `1200` | لا ازدواج؛ يُثبت بمعادلة تجميعية |
| Q5 | **لا تعديل للتاريخ المحاسبي عند إعادة تشغيل التقرير** | تشغيل الأعمار مرتين + مقارنة بصمة القيود وتواريخها قبل/بعد | **لا تغيير** (التقرير قراءة فقط) — يُثبت بلقطات `COUNT`/`SUM` قبل وبعد |
| Q6 | **إغلاق الفاتورة كاملًا** | فاتورة 100 + قبض مخصَّص 100 ⇒ يجب أن تختفي من الأعمار | لا تظهر (المتبقي 0) |

## 6) التوصية وخطة التنفيذ المقترحة (بلا تنفيذ)

**توصية مهنية (يحتاج اعتمادك):**
1. **فورًا (بلا سياسة جديدة، بلا Migration):** إصلاح **شروط الاستعلام** في فرع العملاء: `Status == Posted` + `InvoiceDate <= asOfDate` (Q1/Q2/Q3) + توحيد صيغة المتبقي في `ReportServiceReportsB` — **يقلّص الفجوة ولا يحلها نهائيًا**.
2. **المرحلة الثانية (تحتاج قرارًا + Migration):** إعادة بناء المتبقي للعملاء على **نموذج الموردين** (`Total − Paid − returns − allocations`) مع **مفهوم «غير مخصص»** ⇒ الخيار **C**.
3. **حتى الاعتماد:** يُوصى بـ**عدم استخدام تقرير أعمار العملاء كمصدر للمستحق**، والاعتماد مؤقتًا على **الأستاذ (V3)** أو على المتبقي المحسوب يدويًا للعملاء ذوي القبض/المردود.

**خطة اختبارات الانحدار المقترحة:** Q1–Q6 + S1–S11 + اختبار تجميعي (Σ متبقي = Σ سطور `1200`) + اختبار حتمي يعيد إنتاج فرق M1A (64.80) **يجب أن يفشل قبل الإصلاح ويُغلق بعده**.
