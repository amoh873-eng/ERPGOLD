## 1) ملخص تنفيذي

1. **الهدف:** آلية موثوقة لتخصيص مقبوضات العملاء على فواتيرهم، تمنع ازدواج احتساب المقبوضات/الشيكات/المردودات، وتحافظ على سلامة الأستاذ العام وعدم تغيير معنى `PaidAmount`/`CurrentBalance`.
2. **المبدأ المعماري (من PU-04 المُثبت):** **صفوف التخصيص لا تُنشئ أي قيد محاسبي**؛ القيد الوحيد هو قيد سند القبض نفسه. التخصيص **تصنيف تحليلي** للقبض الموجود محاسبيًا، ولا يُغيّر 1200 ولا رصيد العميل.
3. **الكيان المقترح:** `CustomerPaymentAllocation` بنمط **صفوف الاتجاه** (`Direction = +1/−1`) بلا حذف، مع `ReversalOfAllocationId` و`ReversalDocumentId`، وبلا أي حقل حالة قابل للتغيير (الحالة **مشتقّة**) — مع تقييم مفصَّل للبديل (§3‑3).
4. **اختلافات مقصودة عن مرجع الموردين (مبرَّرة):**
   - **التخصيص اختياري وجزئي**: `ΣA ≤ Amount` (لا يُشترط تساوي المبلغ كاملًا) لأن قرار P0-2G يُلزم بإظهار **المقبوضات بلا تخصيص موثق**؛ بينما PU-04 يشترط `ΣA = Amount` ويعتبر عدمه شذوذًا.
   - **ترتيب FIFO**: `InvoiceDate ASC` ثم **`Id ASC`** (وليس رقم الفاتورة — الرقم للعرض فقط).
   - **لا فهرس فريد على (ReceiptVoucherId, SalesInvoiceId)** — بنفس منطق D13-A/B (صفوف موجبة متعددة + عكوس جزئية متعددة + إعادة توزيع).
   - **تخصيص الشيكات** يحتاج قرارًا منفصلًا (§7‑C4) ولا يُستنتج من وجود `BankCheck.RelatedInvoiceId`.
5. **قواعد التاريخ:** الحفاظ على إصلاح P0-2J (`X < asOf.Date.AddDays(1)`) + شرط التخصيص التاريخي (`AllocatedAt` + تاريخ المستند) لمنع ظهور تخصيص لاحق في تقرير سابق (§6).
6. **التزامن:** معاملة صريحة + أقفال صفوف (`FOR UPDATE`) + فحص مجاميع داخل المعاملة + مفاتيح idempotency بفهارس فريدة مُرشَّحة + سجل تدقيق مُلحَق فقط + عكس بدل الحذف (§9).
7. **الأداء:** احتساب مجمَّع (5 استعلامات ثابتة) داخل `CustomerAllocationQueries`، بلا N+1، وفهارس مقترحة (§10).
8. **لا تخصيصات تاريخية مُخترَعة:** المقبوضات التاريخية تبقى «بلا تخصيص موثق»؛ أي تعبئة تاريخية = خيار منفصل بموافقة صريحة واختبارات مستقلة (§7‑C6).
9. **القرارات المحاسبية المعلَّقة موثَّقة** في §7 و§13 (C1/C3/C4/C5/C6/C7 + D1…D14) — **لا شيء منها نُفِّذ**.

### 3‑4) هل يحتاج الشيك كيانًا منفصلًا؟
يُعالَج في §7‑C4 بثلاثة خيارات؛ والتصميم الموصى به **جدول واحد بنمط «مصدر موحَّد»** (سند قبض **أو** شيك) مع قيد CHECK لمنع ملء المصدرين، **ومنع تمثيل المبلغ مرتين** بقواعد:
1. **مصدر واحد لكل مبلغ:** لا يجوز تخصيص المال نفسه مرتين (سند + شيك) — يُمنع بمنع تعدُّد المصادر على نفس الصف، ويُرصد شذوذ `ΣA > R` و`ΣA > Amount`.
2. **الشيك المرتبط بفاتورة (`BankCheck.RelatedInvoiceId`) لا يُخصَّص آليًا** — الحقل إعلامي اليوم (P0-2E): يبقى كما هو، وإن اعتُمد تخصيص الشيكات فيُستخدم **مسار التخصيص الصريح** لا الحقل الإرثي (مصدر حقيقة واحد).
3. **الفواتير المسدَّدة بشيك** (`PaymentMethod = Check`) لها `PaidAmount = Total` ⇒ متبقيها = 0 ⇒ **لا تُخصَّص أصلًا** (يمنع ازدواج قياس الشيك: مرة في `PaidAmount` ومرة في التخصيص).

## 4) قواعد التخصيص اليدوي وFIFO

### 4‑1) معادلة المتبقي (مصدر الحقيقة الواحد — توسيع `CustomerAllocationQueries`)
```
R(فاتورة) = TotalAmount − PaidAmount − Σ(مردودات مرحَّلة مرتبطة بـOnAccountCredit) − NetAllocated
Available  = max(0, R)
NetAllocated = Σ(Direction=+1) − Σ(Direction=−1)   للمخصَّصات على الفاتورة (حتى تاريخ القطع)
```
- `PaidAmount` **يبقى كما هو** (لا يُحدَّث) — قرار صريح.
- `OnAccountCredit` مقيَّد بقرار §7‑C5 (حاليًا: كل مردود مرحَّل مرتبط — ويُقيَّد بعد اعتماد `SettlementType`).

### 4‑2) التخصيص اليدوي — الشروط الملزمة (كلها داخل معاملة واحدة)
| الشرط | الرسالة/السلوك عند الفشل |
|---|---|
| السند **مرحَّل** (`VoucherStatus.Posted`) وغير محذوف | رفض: «لا يُخصَّص إلا سند قبض مُرحَّل» |
| الفاتورة **مرحَّلة** (`DocumentStatus.Posted`) وغير محذوفة وغير ملغاة | رفض: «فاتورة غير مرحَّلة/ملغاة» |
| **تطابق العميل**: `voucher.CustomerId == invoice.CustomerId == allocation.CustomerId` | رفض: «عدم تطابق العميل» |
| الفاتورة **آجلة** (`InvoiceType == OnAccount`) — النقدية/البطاقة/الشيك مستبعدة (`PaidAmount` يغلقها) | رفض + سبب صريح |
| `Amount > 0` و`≥ 0.01` بعد التقريب | رفض: «مبلغ غير صالح» |
| Σ تخصيصات السند (صافي) + الجديد ≤ `voucher.Amount` | رفض: «يتجاوز المتاح على السند (x)» |
| Σ تخصيصات الفاتورة (صافي) + الجديد ≤ `Available` | رفض: «يتجاوز المتبقي المسموح للفاتورة (x)» |
| لا تعارض مع تخصيص موجود لنفس (سند، فاتورة) **يُسمح به** (صفوف موجبة متعددة) | — (مقصود) |
| **التقريب**: `MoneyRounding` (بنك → ToEven) وكل مبلغ منزلتان | رفض أي فرق تقريب > 0.005 |

**التخصيص الجزئي:** مسموح ومقصود؛ الباقي = «مقبوضات بلا تخصيص موثق» (§5). **التخصيص الكامل** (`ΣA = Amount`) غير مشترط — **خلاف مقصود** عن PU-04.

### 4‑3) FIFO — قواعد التشغيل
1. **عملية صريحة** يطلبها المستخدم (زر/خطوة في شاشة السند) — **ممنوع** تشغيلها خفيًا عند فتح تقرير أو شاشة.
2. **ترتيب حتمي:** `InvoiceDate ASC` ثم **`Id ASC`** (`InvoiceNumber` للعرض فقط) — مأخوذ من قرار P0-2G‑2 ومختلف عن مرجع PU-04 (الذي يفرز بالرقم).
3. تُرشَّح الفواتير المؤهَّلة فقط (`Posted`, `OnAccount`, `Available > 0`, نفس العميل, تاريخ الفاتورة ≤ تاريخ القطع).
4. التوزيع: `take = min(Available, remaining)` لكل فاتورة بالترتيب حتى نفاد مبلغ السند.
5. **فرق التقريب:** القرش المتبقي يُضاف إلى أكبر سطر (ترتيب حتمي) **بشرط** ألا يتجاوز `Available` — وإلا يبقى «غير مخصص».
6. **النتيجة اقتراح قابل للتعديل** قبل التأكيد، ثم تُحفظ كصفوف تخصيص **صريحة** مع سجل تدقيق `FifoApplied` (المبالغ + الترتيب).
7. **ممنوع على المستندات التاريخية:** لا يُشغَّل FIFO على مقبوضات قديمة بلا تخصيص موثق لتوليد تخصيصات (§7‑C6) — والقيود: `AllocatedAt = now` ⇒ إن شُغِّل لاحقًا فسيظهر أثره في التقارير بأثر لاحق (§6) لا رجعي.

### 4‑4) متى يُسمح بالتخصيص؟ (قرار D1)
| البديل | ملاحظة |
|---|---|
| (أ) **عند ترحيل السند فقط** (نمط PU-04) | يمنع تعديل التصنيف بعد الترحيل إلا بعكس/إعادة توزيع؛ أنظف تدقيقيًا |
| (ب) **عند الترحيل + لاحقًا كتصحيح** (مقترح) | يسمح بتصنيف مقبوضات سابقة **بصفوف جديدة** (`AllocatedAt` = الآن) دون مسّ الأستاذ؛ يتطلب صلاحية مستقلة `Vouchers.Allocate` وسجل تدقيق |
| (ج) لاحقًا مخفيًا عند فتح التقرير | ❌ مرفوض (يخالف P0-2G ومبدأ «عملية صريحة») |

## 5) معالجة المقبوضات غير المخصصة

### 5‑1) تعريف قابل للإثبات
```
متاح السند   = Amount − Σ(+1) + Σ(−1)              (صافي، مقرَّب)
غير مخصص (للعميل) = Σ متاح السندات المرحَّلة حتى تاريخ القطع  +  Σ شيكات مقبوضة بلا رابط فاتورة
```
- البند يُعرض **مستقلًا** ولا يُخصم من أي فاتورة إلا عبر صفوف تخصيص فعلية.
- **ممنوع** ربط سند بفاتورة لمجرد تطابق العميل (مثبت في P0-2H/I).
- الوصف المعتمد يبقى: **«مقبوضات بلا تخصيص موثق»** — لا «غير مخصص مؤكد» (لأن التخصيص قد يكون موجودًا في النظام القديم بلا سجل).

### 5‑2) منع الخصم المزدوج (القواعد الملزمة)
| المصدر | الحكم |
|---|---|
| صفوف التخصيص (`+1/−1`) | **الوحيد** الذي يخفّض `R` على الفاتورة |
| «المتاح على السند» | = `Amount − NetAllocated` ⇒ **لا يمكن** أن يظهر المبلغ نفسه مخصَّصًا وغير مخصَّص (العلاقة طرح لا جمع) |
| الشيكات: «بلا رابط فاتورة» | تُحتسب في البند المستقل **فقط** إذا لم تُخصَّص (لا صفوف تخصيص) — وإن اعتُمد تخصيص الشيكات يصبح مصدر الحقيقة هو الصفوف |
| الشيكات «المرتبطة بفاتورة» (`RelatedInvoiceId`) | **لا تُخصم** ولا تدخل «بلا تخصيص موثق» (تجنّب عدّ الشيك مرتين مع `PaidAmount`) — كما في P0-2H/I |
| الفواتير المسدَّدة بشيك/نقدًا | `PaidAmount = Total` ⇒ `Available = 0` ⇒ لا تخصيص ولا بند |
| عهدة المندوبين (C1) | **لا يُخصَّص ولا يُخصم** حتى يُعتمد خيار (بند مستقل أو مصدر تخصيص — §7‑C1) |
| `1102` «تحت التحصيل» | **لا يُضاف** إلى أي طرف (دحض P0-2E) |

### 5‑3) السندات الملغاة/المعكوسة
| الحالة | المعالجة المقترحة |
|---|---|
| مسودة/معتمد | لا تخصيص ولا احتساب (لا قيد) — مُثبت في T6 |
| **ملغى** (`VoucherStatus.Cancelled`) | لا يظهر في أي بند (مُثبت في T7)؛ ولا يجوز أن يحمل صفوف تخصيص (`+1`) ⇒ **لا يُسمح بالتخصيص إلا لسند مُرحَّل**، وإلغاء سند مُرحَّل **مرفوض أصلًا** في الخدمة |
| **معكوس** (`VoucherStatus.Reversed`) | ⚠️ **لا وجود لمسار عكس سند قبض اليوم** (`ReceiptVoucherReversal` غير موجود؛ و`VoucherStatus.Reversed` عرض فقط في `ReceiptVoucherService:134`) ⇒ **قرار مطلوب (§7‑C6/D10):** (أ) إضافة `ReceiptVoucherReversal` بنسخ نمط PU-04 (مستند عكس بقيد معاكس + صفوف `−1` للتخصيصات)، أو (ب) الاكتفاء بعكس **صفوف التخصيص** فقط (تصحيح تحليلي **بلا** عكس الحركة النقدية) — وهذا لا يكفي إذا كان المطلوب إلغاء القبض نفسه |

**قاعدة عامة:** كل إبطال = **صفوف `−1` + مستند عكس (إن وُجد) + سجل تدقيق**، ولا حذف ولا تعديل مبلغ صف قائم.

## 6) سياسة التاريخ والتقارير التاريخية

### 6‑1) الحفاظ على إصلاح P0-2J
`X < asOf.Date.AddDays(1)` — لجميع مقارنات التواريخ (مردودات/فواتير/سندات/شيكات/تخصيصات)، مع مراعاة أن `InvoiceDate`/`EntryDate` من نوع `date` وبقية الحقول `timestamp`.

### 6‑2) الأنواع الأربعة للتواريخ (تمييز إلزامي)
| التاريخ | الحقل | الدلالة |
|---|---|---|
| تاريخ المستند المحاسبي | `InvoiceDate` · `ReturnDate` · `VoucherDate` · `ReceivedOrIssuedDate` | **الأساس** لدخول المستند في تقرير «حتى تاريخ» |
| تاريخ الترحيل | `PostedAt` (timestamp) | يثبت أن المستند كان مرحَّلًا وقته — لا يُستخدم كتاريخ مستند |
| **تاريخ إنشاء التخصيص** | `AllocatedAt` (timestamp) | **الأساس** لدخول التخصيص في تقرير «حتى تاريخ» |
| تاريخ الإلغاء/العكس | `AllocatedAt` لصف العكس + تاريخ مستند العكس | يُخرج أثر التخصيص من التقارير اللاحقة فقط |

### 6‑3) قاعدة منع «أثر رجعي» (D9 — تحتاج اعتماد)
| البديل | الصيغة | الأثر |
|---|---|---|
| **(أ) شرطان معًا (موصى في P0-2G‑1)** | `AllocatedAt < cutoff` **و** `docDate < cutoff` (للسند/الفاتورة/المردود) | تخصيص أُنشئ اليوم لا يظهر في تقرير الأمس **حتى لو كان السند قديمًا** ✅ (الأكثر تحفّظًا) |
| (ب) تاريخ المستند فقط | `docDate < cutoff` | يجعل التخصيص اللاحق **يعيد كتابة** تقرير تاريخي (قديم) ⇒ مرفوض افتراضيًا |
| (ج) `AllocatedAt` فقط | `AllocatedAt < cutoff` | يعرض تخصيصًا لسند لاحق في تقرير أسبق (إن كان السند لاحقًا) ⇒ لا يكفي وحده |

**عكوس التخصيص تاريخيًا:** صف `−1` بـ`AllocatedAt` لاحق ⇒ لا يُسقط التخصيص في تقرير سابق (الصحيح) ويُسقطه في تقرير لاحق ✅ — أي أن النموذج **يدعم إعادة بناء الحالة تاريخيًا** بشرط تسجيل `AllocatedAt` لكل صف.
**قيد موثَّق لا يُفترض حلّه:** إذا أُريد معرفة «حالة التخصيص كما أراها المستخدم في لحظة زمنية» بدقة سلوكية (من خصَّص ماذا ومتى تعديل الاقتراح) فالأدق سجل تدقيق `AuditTrail` وليس صفوف التخصيص — ولهذا يُسجَّل التدقيق لكل عملية تخصيص/عكس/إعادة توزيع.

## 7) تحليل C1 وC3 وC4 وC5 وC6 وC7

### C1 — عهدة المندوبين (`RepCustodyService.Collect`)
**المسار المُتبع (كود):** `CreateAsync(dto, actorUserId)` → `Effect = Collect` ⇒ قيد **مدين 1110** (عهدة نقدية بيد المندوبين) / **دائن 1200** (ذمم العملاء) — بتاريخ `dto.Timestamp`؛ ويُخزَّن `CustomerId` **و`InvoiceId` اختياري** بلا أي أثر محاسبي أو تخصيصي (الحقل إعلامي مثل `BankCheck.RelatedInvoiceId`).
**التصنيف:** حركة **تخفّض 1200** و**قابلة للنسب لعميل** (`CustomerId` مطلوب فعليًا في المسار) لكن **غير مرتبطة بفاتورة بعلاقة تخصيص موثقة** (`InvoiceId` مُخزَّن فقط).
**القرارات المقترحة (لا يُخصم تلقائيًا في كل الأحوال):**
| الخيار | الأثر | المخاطرة |
|---|---|---|
| (أ) **بند مستقل «تحصيل ميداني (عهدة مندوب)»** في التقرير، بلا خصم من الفواتير | يشرح فرقًا قائمًا بين التقرير و1200 (مقاس: 40 في P0-2I‑R6) | زيادة عدد بنود التقرير (مقبول) |
| (ب) **مستند وسيط:** تحويل التحصيل الميداني إلى **سند قبض** (نفس دورة الحياة/القيد) ثم يخضع للتخصيص العادي | توحيد مصدر الحقيقة وتقليل المسارات المتفرقة | تغيير دورة عمل المندوبين + قيد معاكس (يتطلب قرارًا واختبارات) |
| (ج) **مصدر تخصيص ثالث** (`RepCustodyId` في كيان التخصيص) | تخصيص مباشر للعهدة | يزيد تعقيد «مصدر واحد» ويستلزم تعديل قيود المصدر الموحَّد + ترحيل |
**التوصية:** (أ) فورًا عند التنفيذ، مع تخطيط (ب) كمشروع لاحق مستقل — و**لا** خصم تلقائي في أي حال.

### C4 — الشيكات المرتبطة بالفواتير
**دورة الشيك المثبتة (P0-2E — لا تُعدَّل):** تسجيل ⇒ مدين 1102 / **دائن 1200** (فيخفّض الذمم فورًا) · إيداع ⇒ **بلا قيد** · تحصيل ⇒ مدين 1101/دائن 1102 · ارتداد ⇒ **مدين 1200**/دائن 1102 · لا حالة إلغاء · حراس منع تكرار فعّالة.
**حقيقة حاكمة:** ظهور `RelatedInvoiceId` في شاشة/سجل **لا يثبت** تخصيصًا محاسبيًا (مُثبت في P0-2E: سُجِّل ولم يُخصم)؛ وهو حقل إرثي إعلامي.
**خيارات التصميم:**
| الخيار | التخصيص | أثر 1200 | المخاطر/الملاحظات |
|---|---|---|---|
| (أ) **لا تخصيص للشيكات** (الوضع الحالي + عرض) | لا صفوف؛ تُعرض في «مرتبط بفاتورة (عرض فقط)» أو «بلا رابط» | لا يتغير | يبقى فرق مُفسَّر بين `R` و1200 بمقدار الشيكات المرتبطة — معلن لا مسوّى |
| (ب) **جدول واحد بمصدر موحَّد** (`ReceiptVoucherId` أو `BankCheckId`) | صفوف تخصيص للشيك (تسجيل `+1`) | لا يتغير (التخصيص تحليلي) | يحتاج قيد CHECK للمصدر + منع ازدواج مع `PaidAmount` (فواتير الشيك) + قرار «هل يخصَّص شيك مسجَّل قبل التحصيل؟» (**موصى: نعم يُخصَّص عند التسجيل لأنه يخفّض 1200 عند التسجيل**، مع إظهار حالة الشيك في العمود) |
| (ج) **مستند وسيط**: كل شيك يُسجَّل عبر **سند قبض** (ثم قيد 1102) | تخصيص موحَّد على السندات فقط | لا يتغير | يغيّر دورة الشيك (ممنوعة في هذه المهمة) + تكرار تسجيل ⇒ **غير موصى به** |
**قيود إلزامية في أي خيار:** لا يُخصَّص شيك **مرتجع** (`Bounced`) · لا يُخصَّص مرتين (سند + شيك) · لا يُخصَّص شيك على فاتورة `PaidAmount = Total` · ولا يُستخدم `1102` في أي طرف من المعادلة.

### C5 — المردودات و`OnAccount`
**نتيجة موثقة لمعنى الحقل ومكانه في المصدر الحالي (ثلاثة مواضع مختلفة بالاسم نفسه!):**
| الموضع | التعريف | الأثر الفعلي |
|---|---|---|
| `SalesInvoiceType.OnAccount` | **نوع الفاتورة** (آجلة) | يحدد حساب المدين في قيد البيع: `OnAccount ⇒ 1200` · `Cash ⇒ 1100` · `Card ⇒ 1205` · `Check ⇒ 1102` |
| `SalesPaymentMethod.OnAccount` | **أداة السداد** (آجل) | تحويل منطقي: `type == OnAccount && method == Cash ⇒ method = OnAccount` |
| `PurchaseReturnSettlementType.OnAccountCredit` (موردين فقط) | **نوع تسوية المردود**: يخفض مدينيات المورد (`2200`) مقابل `CashRefund` (رد نقدي 1100) | **سابقة PU-04 الصحيحة للتمييز** |

**الخلل البنيوي المؤكد (C5):** `SalesReturn` **لا يحمل أي حقل نوع تسوية**؛ و`SalesReturnService.Create` يختار الحساب الدائن **من نوع الفاتورة الأصلية**:
```
invoice.InvoiceType == OnAccount ? 1200 : (POS+Cash ? 1105 : 1100)
```
⇒ (1) مردود فاتورة آجلة = **دائن 1200** · (2) مردود فاتورة نقدية = دائن 1100/1105 ⇒ **لا يمسّ 1200**.
**الأثر على المتبقي ومقارنته بالأستاذ:** صيغة P0-2H/J تخصم المردود من متبقي **كل** فاتورة مرحَّلة بلا تمييز النوع؛ وبالنسبة للفاتورة النقدية يكون الطرح **بلا معنى محاسبي** (فاتورتها أصلاً `PaidAmount = Total` ⇒ متبقيها 0، ويُخفيه شرط الاستبعاد `≤ 0.01`) ⇒ **أثر عملي مخفي اليوم لكنه هشّ**: يتحوّل إلى خطأ ظاهر إذا غُيِّر شرط الاستبعاد أو اعتُمد عرض الائتمان أو أُضيف بند «مردودات نقدية».
**ما يجب أن يؤثر في المتبقي:** يُخصَّص الطرح على مردودات **`OnAccountCredit` فقط** (التي خفّضت 1200 فعلًا).
**الحالات التي تحتاج قرارًا محاسبيًا إضافيًا:**
1. **مردود فاتورة آجلة مُسدَّدة نقدًا لاحقًا** (المطلوب: رد نقدي للعميل) — غير ممثَّل اليوم (يُقيَّد دائمًا ضد 1200) ⇒ يحتاج `CashRefund` + مرجع إثبات كما في الموردين.
2. **مردود يكسر الأداء عن الرصيد** — حاليًا `Customer.CurrentBalance -= TotalAmount` **غير مشروط بنوع التسوية** (انحراف موثَّق في P0-2B/P0-2G) ⇒ يجب أن يُراجَع مع إضافة `SettlementType` (قرار منفصل لأنه يمسّ رصيدًا تشغيليًا).
3. **`PaidAmount = Total` للنقدي/الشيك** يعني أن مردود هذه الفواتير لا يظهر في أي متبقي — هل نعرضه بندًا مستقلًا؟ (قرار عرض).
**التوصية:** إضافة `SalesReturn.SettlementType` (`OnAccountCredit` افتراضيًا + `CashRefund` مع `RefundReference`) بنسخ سابقة PU-04 ⇒ **يستلزم Migration ⇒ مؤجَّل لموافقة (D6)**، وتقييد الطرح في `CustomerAllocationQueries` بـ`OnAccountCredit` بعد الترحيل.

## 8) نموذج الأرصدة الدائنة (موسَّع بصفوف التخصيص)

### 8‑1) السلّم الحسابي (مكوّنات **لا تُجمع** بل تُطرح)
```
(1) Σ المتبقي المحسوب (بعد التخصيص)   = Σ max(0, R(فاتورة))        → يظهر في تقرير الأعمار
(2) (−) مقبوضات بلا تخصيص موثق         = Σ متاح السندات المرحَّلة
(3) (−) شيكات مقبوضة بلا رابط فاتورة   = Σ شيكات مستلمة غير مرتجعة غير مخصَّصة
(4) (−) شيكات مرتبطة بفاتورة (إن بقيت بلا تخصيص) = تصحيحي معلَّم
──────────────────────────────────────────────────────────────
(=) المنسوب من مستندات التقرير إلى 1200 = (1) − (2) − (3) − (4)
(5) رصيد 1200 من الأستاذ العام
(6) الفرق غير المفسَّر                = (5) − (=)
      مكوّناته: عهدة المندوبين (قابل للنسب) · قيود يدوية/افتتاحية (غير قابل) · فروق زمنية
```

### 8‑2) الرصيد الدائن المحسوب للعميل (يحتاج اعتمادًا — D5)
```
رصيد دائن محسوب(عميل) = max(0, [(2)+(3)] للعميل − (1) للعميل)
```
**الشروط الملزمة:**
1. يُحسب **لكل عميل** من مستنداته فقط، ويُوسَم **«دائن محسوب من المستندات — غير مؤكد»**.
2. **لا** يُشتق من متبقٍّ سالب لفاتورة واحدة (سياسة صريحة في المهمة).
3. **لا** يدخل في (1) ولا يُجمع معه (وإلا خُصم القبض مرتين).
4. لا يُنشئ أي قيد أو رصيد محاسبي، ولا يُغيّر `CurrentBalance`.
5. وجود الفرق غير المفسَّر لا يُسوَّى ولا يُوزَّع على العملاء.

### 8‑3) أمثلة مقيسة من P0-2I/J (مرجع للاختبارات)
| السيناريو | القياس المثبت | ما يعرضه السلّم |
|---|---|---|
| فاتورة 100 + قبض 150 | `1200 = −50` والتقرير يعرض 100 + بند 150 | (1)=100 · (2)=150 · (6) يشرح الفرق · **دائن محسوب = 50** عند اعتماد D5 |
| إعادة تخصيص 30 من (2) إلى (1) | `1200` لا يتغير (لا قيد) | (1) 130 · (2) 120 · **المجموع ثابت** ✅ |
| عهدة مندوب 40 | `1200` نقص 40 والتقرير لم يتغيّر | (6) يشرح 40 (C1) |
| شيك مرتبط 10 | `1200` نقص 10 والتقرير يظهره «عرض فقط» | (4)=10 تصحيحي |

## 9) حماية التزامن وسلامة البيانات

### 9‑1) ذرّية «تحقق + تخصيص + حفظ» (نمط المشروع المُثبت)
```
DbTransactionHelper.ExecuteAsync(context, async () => {          // بلا إعادة محاولة صامتة
  1) قفل صف العميل      : PartyRowLock.LockCustomerAsync(customerId)          // FOR UPDATE
  2) قفل صف السند       : SELECT 1 FROM "ReceiptVouchers" WHERE "Id" = @v FOR UPDATE
  3) قفل صفوف الفواتير  : SELECT 1 FROM "SalesInvoices" WHERE "Id" IN (…) ORDER BY "Id" FOR UPDATE
                          (ترتيب تصاعدي ثابت لمنع الجمود/deadlock)
  4) قراءة مجمَّعة      : NetAllocated للسند + Available لكل فاتورة (استعلام واحد لكل مجموعة)
  5) التحقق             : Σ_send ≤ Amount − NetAllocated(voucher)  و  Σ_invoice ≤ Available(invoice)
  6) الإضافة            : صفوف CustomerPaymentAllocation (+ تدقيق append-only)
  7) SaveChanges + Commit
});
```
- **مستوى العزل:** الافتراضي في PostgreSQL (`READ COMMITTED`) كافٍ **مع** أقفال الصفوف الصريحة (النمط المعتمد في `ReceiptVoucherService`/`PaymentVoucherService`/`PartyRowLock`)؛ لا حاجة لـ`SERIALIZABLE` (سيتطلب إعادة محاولة على كل تعارض).
- **`RowVersion` غير كافٍ** كأداة منع (لا يولّد الخادم قيمته على `bytea`) ⇒ المنع بالأقفال + الفحوص المجمَّعة داخل المعاملة.

### 9‑2) الفهارس الفريدة والقرار D14
| الفهرس | الغرض | ملاحظة |
|---|---|---|
| `UX_CustomerAllocations_IdempotencyKey` (مُرشَّح) | منع تكرار «نية» طلب التخصيص | عند انتهاكه ⇒ إعادة النتيجة القائمة (نمط `UniqueViolation.IsOnIndex`) |
| `UX_ReceiptVouchers_IdempotencyKey` (إن اعتُمد) | منع تكرار ترحيل/تخصيص السند نفسه | نفس نمط PU-04 |
| `UX_…ReversalDocument_Original` (مُرشَّح) | مستند عكس واحد لكل سند أصلي | إن أُضيف `ReceiptVoucherReversal` (§7‑C6) |
| ❌ **لا** فهرس فريد على `(ReceiptVoucherId, SalesInvoiceId)` | لأنه **يمنع** تخصيصات جزئية متعددة لنفس الزوج وإعادة التخصيص بعد العكس | **قرار موثَّق (D14)**؛ البديل: قيد جزئي `WHERE Direction = +1 AND IsDeleted = false` **لا يُنصح به** لأنه يمنع التقسيم الجزئي المتكرر |

### 9‑3) منع تجاوز المتاح — طبقتان
1. **داخل المعاملة (الإلزامي):** فحص المجاميع بعد الأقفال (يضمن الذرّية مع الطلبات المتزامنة).
2. **رصد قراءة فقط (نمط `AllocationAnomalyKinds` PU-04):** أنواع الشواذ المقترحة لمراجعة دورية:
   `SumMismatch(ΣA > Amount)` · `ExceedsAvailable(ΣA > R)` · `MissingVoucher` · `MissingInvoice` · `CustomerMismatch` · `DuplicateSource(سند+شيك لنفس المبلغ)`.

### 9‑4) إعادة الطلب (Idempotency) والتدقيق والإبطال
| البند | التصميم |
|---|---|
| إعادة الطلب | `IdempotencyKey` على طلب «التخصيص/العكس/إعادة التوزيع» + فهرس فريد مُرشَّح + إرجاع النتيجة القائمة بدل التكرار |
| التدقيق | صفوف `AuditTrail` **في نفس المعاملة** (`VoucherAuditTrailWriter.Write` لسند القبض + كاتب مماثل للتخصيص): أفعال `Allocated` · `FifoApplied` · `Reversed` · `Reallocated` + المبالغ ومرجع الفاتورة |
| الإلغاء/العكس | **صفوف `−1`** + `ReversalOfAllocationId` + (مستند عكس إن وُجد) + تدقيق؛ **بلا حذف** و**بلا تعديل مبلغ صف** |
| ضمانات البنية | CHECK constraints (مبلغ موجب · اتجاه ∈ {1,−1} · شكل العكس · مصدر واحد) + `Restrict` على كل المفاتيح |
| الفشل | `DocumentFailureCleanup` + معاملة تُتراجع بالكامل ⇒ لا صفوف جزئية ولا أثر تدقيقي معلَّق |

## 10) الأداء وواجهات النظام

### 10‑1) احتساب مجمَّع (بلا N+1)
| الاستعلام | الشكل | العدد |
|---|---|---|
| المردودات المرحَّلة | `GROUP BY SalesInvoiceId` حتى القطع | 1 |
| التخصيصات الصافية | `GROUP BY SalesInvoiceId` — `SUM(CASE WHEN Direction=1 …) − SUM(…=-1)` | 1 |
| الفواتير + بيانات العميل | استعلام واحد بـJOIN | 1 |
| سندات القبض + المُخصَّص لكل سند | `GROUP BY ReceiptVoucherId` | 1 |
| الشيكات (بلا رابط + مرتبط) | استعلام واحد | 1 |
⇒ **5 استعلامات ثابتة** (الحالي 4 قبل إدخال صفوف التخصيص) مهما كان عدد المستندات — يُقاس بنفس أسلوب P0-2H (`CountingReaderInterceptor`).
**فهارس مساندة:** `(SalesInvoiceId, Direction)` · `(ReceiptVoucherId)` · `(CustomerId, AllocatedAt)` (مقترحة في §3‑3) — بلا فهرسة عشوائية، وتقاس قبل أي إضافة.

### 10‑2) أثر التصميم على الواجهات (بلا تغيير معنى أي حقل قائم)
| الواجهة | الأثر المقترح | التزام |
|---|---|---|
| **تقرير أعمار الذمم** | `R` يخصم `NetAllocated` (يظهر أثر التخصيص)؛ تُضاف حقول عرض اختيارية: «مخصَّص» و«متاح» | لا تغيير في معنى `Rows/الفئات` |
| **كشف حساب العميل** | يُقترح لاحقًا إضافة سطور السندات/التخصيصات (اليوم: فواتير + مردودات فقط) | قرار منفصل (يغيّر أرقام الكشف) |
| **شاشة سند القبض** | لوحة تخصيص (فواتير مؤهَّلة + مُدخل المبلغ + FIFO اختياري + عرض «المتبقي بلا تخصيص») | إضافة، بلا كسر |
| **شاشة الفاتورة** | عرض التخصيصات المرتبطة + «مخصَّص/متاح» | إضافة |
| **التقارير المحاسبية** | **لا تغيير** (التخصيص بلا قيود ⇒ ميزان المراجعة/الأستاذ كما هو) | إلزامي |
| **API والموبايل** | **لا يوجد أي كود تخصيص** في `src\Api`/`src\Mobile` (تحقق فعلي: 0 نتيجة) ⇒ لا كسر؛ أي إضافة لاحقة تكون متوافقة (حقول جديدة فقط) + قرار تماثل API | لا تغيير معنى الحقول |
| **الصلاحيات والتدقيق** | فعل جديد `Vouchers.Allocate` (نمط `VoucherRules.Permission`) + `CanReverse()` للعكس (فشل مغلق) + تدقيق append-only | لا دور جديد إلزامي |
| `Customer.CurrentBalance` · `SalesInvoice.PaidAmount` | **لا يُغيَّر معناهما ولا يُحدَّثان** في هذا التصميم | إلزامي |

- **لا حذف** أي بيانات أو فهارس قائمة.

4. **لا نشر إنتاج** قبل مراجعة مالك النظام.

## 14) قائمة صريحة بما لم يُنفَّذ (في هذه المهمة)

✅ **لم يُنشأ** كيان `CustomerPaymentAllocation` ولا أي جدول/عمود/فهرس · ✅ **لا Migration** ولا تعديل مخطط (آخر ترحيل قائم `20261022192835_Pu04SupplierPaymentAllocation` كما هو) · ✅ **لم يُنشأ أي تخصيص فعلي** ولا FIFO · ✅ **لا تغيير** لأي قيد أو رصيد تاريخي · ✅ **لا تعديل** لـ`PaidAmount` ولا `Customer.CurrentBalance` · ✅ **لا تعديل** لـ`BankCheckService` ولا دورة الشيك · ✅ **لا تغيير** API/الموبايل/الواجهات · ✅ **لا تعديل** لتقارير الموردين · ✅ **لا نشر/VPS/إنتاج** · ✅ **لا Git** (add/commit/push) · ✅ **لم تبدأ PU-05** ولا تنفيذ المرحلة B · ✅ **لم تُشغَّل أي اختبارات** (لا حاجة مثبتة — التصميم قُرئ من الكود) · ✅ المخرَج الوحيد: **هذه الوثيقة**.

**تنبيه معماري محتمل (يُوقف العمل عنده إن اعتُمد):** أي قرار يقضي بـ**نقل الدفعات المقدمة إلى حساب محاسبي مستقل** (C7‑ج) أو بتغيير **دورة الشيك** (C4‑ج) هو **تغيير معماري/محاسبي أساسي** يتطلب **مراجعة معمارية وموافقة مالك النظام قبل أي تصميم تنفيذي** — ولم يُفترض في هذا التصميم.

## 15) الخلاصة

- التصميم **جاهز للمراجعة** ومبنيّ على **سابقة مُثبتة** (PU-04) مع **اختلافات مقصودة موثَّقة** محدَّدة الأسباب.
