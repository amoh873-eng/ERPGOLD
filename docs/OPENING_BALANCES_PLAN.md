# خطة الأرصدة الافتتاحية المحاسبية (Phase B — تصميم فقط، غير مُنفَّذ)

> هذه وثيقة تصميم. **لم يُكتب أي كود لهذه الميزة**، ولم تُعدَّل أي أرصدة أو بيانات.
> القرار المطلوب قبل التنفيذ: الموافقة على هذا التصميم وخطة اختباره أولاً.

## 1) الهدف والنطاق

إتاحة إدخال **أرصدة افتتاحية محاسبية** رسمية عبر **قيد افتتاحي متوازن** واحد، يمرّ عبر نفس
نقطة الاختناق المحاسبية الموجودة، دون أي كتابة مباشرة على `Account.CurrentBalance`.

**خارج النطاق:** نقل القيود التاريخية، تعديل أرصدة قائمة، ترحيل مخزون افتتاحي بكميات (يُعالَج
منفصلاً)، أي تغيير في قواعد النسخ المنشورة.

## 2) القرار المعماري: إعادة استخدام الموجود (بلا إطار تحقق جديد)

نقطة الدخول الإلزامية هي الموجودة أصلاً: `JournalEntryService.PrepareEntryAsync`
(تتحقق من التاريخ، توازن القيد، ومنع الحسابات الرئيسية، وتحدّث الأرصدة **ذرّياً**، وتُصدر
الرقم عبر `NumberSequenceHelper.NextAsync`). القيد الافتتاحي **لا** يكتب أرصدة بنفسه.

المكوّنات المقترحة:

1. **Domain:** إضافة `JournalEntryType.OpeningBalance = 17` (تمييز نوع القيد للأرشفة والتقارير).
2. **مستند افتتاحي** `OpeningBalanceBatch` (كيان جديد) يحمل: السنة المالية، الحالة
   (`Draft` / `Posted`)، `JournalEntryId`، وحقول التدقيق من `BaseEntity`
   (`CreatedAt/CreatedBy/UpdatedAt/UpdatedBy/IsDeleted`). وجود المستند يحلّ «منع التكرار».
3. **خدمة** `OpeningBalanceService` (Application):
   - تُدخل بنوداً صريحة: (رقم حساب، مدين، دائن) — **لا تُخترع** حساباً مقابلاً.
   - تُحوّل كل «رقم حساب» إلى حساب متحرك عبر `PostingAccountResolver.ResolveAsync`
     (المستخدمة فعلاً)، فإن لم يوجد الرقم أو كان **رئيسياً (Parent)** ⇒ رفض صريح برسالة
     مفتاحية (على نمط `ErrorLocalizer`/`IResourceKeyedError`).
   - تُمرّر البنود كما هي إلى `PrepareEntryAsync` فتحصل مجاناً على: حارس التاريخ، تحقق
     التوازن، قاعدة «الحسابات المتحركة فقط» عبر `MovementAccountValidator`، الترقيم الآمن،
     والتحديث الذرّي للأرصدة.
4. **الحساب المقابل (Opening Balance Equity):** يجب أن يُمرَّر **رقم حسابه صراحةً** ضمن البنود
   (فيبقى القيد متوازناً). لا يُفترض أي رقم أو حساب غير موجود؛ وإن غابت جهة الموازنة ⇒ رفض
   «القيد غير متوازن» من نفس الحارس المركزي.
5. **UI:** شاشة واحدة تحت موديول المحاسبة: جدول بنود (حساب/مدين/دائن) + عرض مجموع المدين
   والدائن والفارق المباشر + زر «ترحيل» لا يُفعَّل إلا عند التوازن (تاريخ افتراضي = اليوم).

## 3) الفترة المالية ومنع التكرار

- **الفترة:** لا يوجد كيان `FiscalPeriod` في المعمارية الحالية؛ لذا نعتمد «سنة مالية» صريحة
  في المستند الافتتاحي، ويُقيَّد تاريخ القيد داخل السنة نفسها عبر حارس التاريخ المركزي.
- **منع التكرار:** قيد فريد على `OpeningBalanceBatch(FiscalYear)` في قاعدة البيانات
  (Unique Index)، إضافةً إلى فحص خدمي مسبق. ترحيل افتتاحي سابق لنفس السنة ⇒ رفض واضح
  (لا تعديل، لا حذف للقيد المُودَع).

## 4) الصلاحيات والمراجعة والتدقيق

- **الصلاحية:** إعادة استخدام نمط الصلاحيات الموجود (`PermissionCatalog` +
  `ManualPriceRules`/`IManualPriceAuthorization`): واجهة تصريح في Application تُنفَّذ في
  Web/Api. الإذن المطلوب: `Accounting.Add` للإنشاء و«ترحيل» مقيّد بدور/إذن `Accounting.Edit`.
  الصلاحية تُحقن من الاستضافة، فلا يمكن تجاوزها من الواجهة.
- **المراجعة:** دورة `Draft → Posted`؛ لا يمكن تعديل المستند بعد الترحيل. أي تصحيح لاحق
  يكون بـ**قيد عكسي** (`JournalEntryType.Manual` أو عكسي) — لا حذف ولا تعديل أرصدة.
- **التدقيق:** `CreatedBy/UpdatedBy` على المستند + بقاء القيد في دفتر القيود للأبد (شفافية).

## 5) العلاقة بميزان المراجعة وأرصدة الحسابات

- `ReportService.GetTrialBalanceAsync` يُجمّع **بنود القيود** (`JournalEntryLine`) لا
  `CurrentBalance` ⇒ القيد الافتتاحي يظهر تلقائياً في ميزان المراجعة دون أي عمل إضافي.
- `Account.CurrentBalance` يبقى **الذاكرة المخزَّنة (cache)** التي تُحدَّث حصراً من
  `PrepareEntryAsync` (المسار الذرّي). لا يوجد أي مسار يكتب الرصيد مباشرة.

## 6) الضمانات المطلوبة (قبول التصميم)

| المطلوب | كيف يتحقق |
|---|---|
| قيد افتتاحي متوازن | `PrepareEntryAsync` (Σمدين = Σدائن) |
| الحسابات المتحركة فقط | `PostingAccountResolver` + `MovementAccountValidator` |
| فترة مالية ومنع تكرار | السنة في المستند + Unique Index على (FiscalYear) |
| صلاحيات/مراجعة/تدقيق | واجهة تصريح مُحقَنة + دورة Draft→Posted + حقول BaseEntity |
| ارتباطه بميزان المراجعة | التقرير يُبنى من بنود القيود مباشرة |
| لا كتابة `CurrentBalance` مباشرة | الكتابة الوحيدة عبر المسار الذرّي في `PrepareEntryAsync` |
| لا افتراض حساب مقابل/رقم غير موجود | البنود صريحة + رفض الرقم غير الموجود/الرئيسي |

## 7) خطة الاختبار (تُنفَّذ عند الموافقة — PostgreSQL معزول كما في Phase A)

1. **توازن:** بنود متوازنة تُقبل وتُنشئ قيداً واحداً؛ بنود غير متوازنة تُرفض ولا يُترك أي أثر.
2. **حساب رئيسي:** إدخال رقم حساب Parent (مثل `1100` في شكل Commercial) يُرفض برسالة مفتاحية.
3. **رقم غير موجود:** رقم حساب غير موجود يُرفض ولا يُبتلع بصمت.
4. **منع التكرار:** ترحيل افتتاحي ثانٍ لنفس السنة المالية يُرفض (Unique + فحص خدمي).
5. **الصلاحية:** مستخدم بلا `Accounting.Add` لا يستطيع الإنشاء؛ وبلا `Accounting.Edit` لا يستطيع الترحيل.
6. **الاتساق:** بعد الترحيل، رصيد كل حساب مخزَّن == دفتر القيود (نفس `LedgerInvariants.AssertConsistentAsync`)،
   وميزان المراجعة يعكس البنود، والمجموع مدين == مجموع دائن.
7. **عدم الكتابة المباشرة:** التأكد أن `CurrentBalance` يتغيّر فقط كنتيجة ترحيل قيد (لا يوجد UPDATE مباشر في الخدمة).
8. **العكس:** قيد عكسي يعيد الأثر ويُبقي الدفتر متوازناً، دون حذف القيد الأصلي.

## 8) أثر التنفيذ عند الموافقة

- Migration واحد لإضافة `JournalEntryType.OpeningBalance` والمستند الافتتاحي + الفهرس الفريد.
- شاشة واحدة + خدمة واحدة. لا تعديل على مسارات Phase A. لا نشر، ولا لمس أي قاعدة منشورة.
